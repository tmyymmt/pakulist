# Xにおける他アカウント投稿データの正規取得・利用経路

調査日: 2026-08-12

## 1. 結論

pakulistの主ユースケースは、**異なる複数アカウント**が投稿した重複・類似文面を比較することである。したがって、利用者自身のXアーカイブだけを入力にしても、原則として比較対象が不足し、UC-01およびUC-02を満たせない。

後続フェーズで他アカウント投稿を取得する場合の候補は、**X公式APIを使う取得経路だけ**とする。画面のスクレイピング、ブラウザ自動操作、第三者が規約に沿って取得したことを確認できないデータセットは採用しない。ただし、XのDeveloper Policyは、X APIまたはX Contentを使ってポリシー違反行為・コンテンツを識別または分析するサービスについて、**Xの明示的な書面許可なしに提供・公開することを禁じている**。そのため、pakulistがX APIを用いて重複投稿候補を収集・分析する機能を提供する前に、想定ユースケースをXへ開示し、書面による許可を得ることを必須のゲートとする。[4]

## 2. 取得経路の比較

| 経路 | 取得できる範囲 | 利点 | 主な制約・リスク | 判断 |
| --- | --- | --- | --- | --- |
| 利用者自身のXアーカイブ | 原則として利用者自身のアカウント関連データ | 公式のエクスポートであり、現行MVPのローカル入力に適合する | 他アカウントとの比較に必要なデータを単独では満たせない | 補助的な入力に限定する |
| 利用者が正当に保有・提供する複数アカウント分の投稿ファイル | 提供者・利用目的・取得根拠に依存する | API実装なしで現行MVPを使える | 取得根拠、提供権限、保存・再配布の条件を個別に確認する必要がある | 現行MVPではこの経路のみ受け入れる |
| X API Recent Search | 過去7日間の公開Post。最大100件/リクエスト | 公式APIであり、小規模な検証・最新候補の収集に適する | Developer Account、アプリ、トークンが必要。レート制限と使用量課金に従う。違反分析サービスには書面許可が必要 | 許可取得後の最初のAPI候補 |
| X API Full-Archive Search | 2006年以降の公開Post履歴。最大500件/リクエスト | 長期の時系列比較と過去候補の検出に対応できる | Pay-per-useまたはEnterpriseの利用資格、費用管理、レート制限、書面許可が必要 | Recent Searchの検証後に必要性を判断する |
| X API Filtered Stream | ルールに一致する新規Postをほぼリアルタイムで受信 | 将来の継続監視に利用できる | 自動収集・継続保存を伴う。現行MVPの対象外であり、保存・削除・通知設計が必要 | 現時点では採用しない |
| スクレイピング・ブラウザ自動操作 | 画面上に表示される内容 | API契約なしで見えるように思える | X公式の開発者ガイドラインが「公式APIのみ」を確認項目としている。規約、安定性、アカウント保護の面で採用できない | 不採用 |

## 3. 公式APIで確認できた条件

XのSearch Postsでは、Recent Searchは過去7日間を対象にすべての開発者へ提供され、Full-Archive Searchは全履歴を対象にpay-per-useおよびEnterprise顧客へ提供される。`from:`などのクエリ演算子で特定アカウントのPostに絞り込める。[1]

レート制限はエンドポイント・認証形態ごとに異なる。公式ドキュメントでは、Recent Searchはアプリ単位450回/15分・ユーザー単位300回/15分、Full-Archive Searchはアプリ単位1回/秒かつ300回/15分と示されている。429応答時はリセット時刻を確認して待機し、バックオフする必要がある。[2]

X APIは使用量ベースの課金とクレジット購入を案内している。料金・アクセス階層は変更され得るため、実装着手時にDeveloper Consoleと契約条件を再確認し、固定の料金やアクセス可否をコード・仕様へ埋め込まない。[3]

XのDeveloper Policyによれば、Developer Accountの申請時には利用目的の説明が必要であり、実質的に異なる利用目的へ変更する場合は事前の通知と承認が必要である。また、APIキーやトークンの第三者共有は禁止され、レート制限の回避も禁止されている。[4]

## 4. データ利用・表示・保存の制約

X APIから取得したPostをサービスで表示する場合は、最新状態を維持し、PostがAPIで利用不可になった場合は合理的に速やかに、またはXもしくは対象アカウントからの削除要求後24時間以内に削除する必要がある。X Contentを第三者へ再配布する場合は原則としてPost ID・User IDだけに制限され、例外的に非自動のダウンロード等で1利用者あたり1日500件までのPost ObjectまたはUser Objectの提供が認められる条件が示されている。[4]

したがって、後続サービスでは次の原則を採用する。

| 原則 | 方針 |
| --- | --- |
| 最小取得 | 事案単位で指定された期間・アカウント・キーワードに限定する。全量収集や無差別監視は行わない。 |
| 最小保持 | API取得Postの保存は、許可済みの用途・保持期間・削除要求処理が設計された後に限定する。現行MVPは保存しない。 |
| 最小再配布 | 出力の既定値はPost ID、URL、アカウント、判定根拠とする。本文を含む出力はXの条件、利用者権限、件数上限、必要な許可を確認してから有効化する。 |
| 表示の最新性 | API取得Postを再表示する機能は、利用不能・削除・保護化を検知して非表示または削除できる設計を必須とする。 |
| 認証情報保護 | Bearer Tokenなどの資格情報をブラウザや入力ファイルに含めず、サーバー側の秘密情報管理だけで扱う。 |

## 5. pakulistで採用する段階的方針

### 5.1 現行OSS MVP

現行MVPは、利用者が正規に取得したCSV/JSONをブラウザで選択する`FilePostProvider`相当の入力だけを維持する。X API、認証、課金、自動収集、サーバー保存、自動通報は実装しない。利用者自身のアーカイブだけでは主ユースケースを満たさないことを、READMEと入力ガイドで明確にする必要がある。

### 5.2 外部取得機能の着手ゲート

次のすべてを満たすまで、pakulistはX APIを使った取得機能を提供しない。

1. Xへ提出する利用目的に、重複投稿の候補収集・分析・表示の範囲を正確に記載し、必要な書面許可を取得する。
2. 利用するAPIアクセス、料金、利用上限、予算上限、超過時の停止条件を決定する。
3. Issue #9で、取得対象、保存期間、削除・保護化への追従、認証情報、出力・再配布、監査ログの方針を確定する。
4. Issue #3で、許可済みデータソースから標準`Post`形式への変換仕様とテストを実装する。

### 5.3 許可取得後の最初の実装候補

最初の候補は、利用者が明示的に指定した期間・キーワード・対象アカウントについて、X API Recent Searchから過去7日間の候補を取得する**オンデマンド・一回限りの検索**である。継続ストリーム、定期実行、全履歴検索、複数アカウントの無差別収集は含めない。

Full-Archive Searchは、Recent Searchでは足りないことが利用者検証で示され、pay-per-useまたはEnterpriseの契約条件・予算・許可が確定した場合にだけ追加判断する。
