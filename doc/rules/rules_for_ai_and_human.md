# AI・人間共通の作業/編集ルール

本ルールは AI と人間の双方に適用する

## 言語
- ドキュメントは日本語で記述・統一する

## ドキュメント配置
- ファイルやフォルダの構成は `README.md` に記載する
  - 常に内容を最新に保つこと
  - `doc/` 以下は全てのファイルを記載する
  - 実装系のフォルダはファイル単位やサブフォルダは記載しない
- 調査結果は `doc/research/` に置く
- 全仕様は `doc/specs/` に置き、内容の種別ごとにサブフォルダで分類する
  - ビジネス要件、システム要件、システムの仕様、概要設計、方式設計、詳細設計（必要なものだけ）はフォルダを分けること
  - フォルダ名は英語とし、標準カテゴリの対応は以下:
    - ビジネス要件: `business_requirements/`
    - システム要件: `system_requirements/`
    - システムの仕様: `system_spec/`
    - 概要設計: `overview_design/`
    - 方式設計: `architecture_design/`
    - 詳細設計: `detail_design/`
  - 上記6カテゴリに収まらない領域は専用カテゴリを追加する現状の追加カテゴリは以下:
    - マーケティング: `marketing/`
    - 価格設計（マネタイズ・価格・ABテスト）: `pricing/`
    - 計測（KPI・イベント計測）: `measurement/`
  - 複数カテゴリを横断する全体メモは `doc/specs/` 直下に置いてよい（例: `important.md`）
- システム改修時の変更点のみ記載した仕様等は `doc/issues/` 以下にissue単位でフォルダを作成し、その中にファイルを作成して記載する
  - フォルダの命名規則は「YYYYMMDD_NN_issueの概要説明の英語」
  - issueの作業が完了する直前の作業として、全仕様にも必ず反映する
- ルールは `doc/rules/` に置く
- 調査・仕様・ルールは、それぞれ適切なフォルダに分ける

## ドキュメント記載
- ドキュメントは新卒のエンジニアでも疑問を持たずに作業を進められるレベルで記載する

## issuesの作業時
- 突発的な作業中断にも耐えられるように、handoverファイルを作成し、1作業が完了するたびにそのファイルに記入する
  - doc/issues/*/work_plan.md を実施する場合は同フォルダにyyyymmdd_*-handover.mdとしてhandoverファイルを作成する

## ファイル分割
- 1ファイルに詰め込みすぎず、内容ごとに適切な単位で分割する
- 既存ファイルの役割に合わない内容は、無理に追記せず新しいファイルに分割する

## 仕様の明文化
- 画面や機能の初期状態・既定値のような操作起点は、必ず仕様に明記して曖昧さを残さない

## 編集時の進め方
- 変更時は、調査・仕様・ルールのどれに属する内容かを先に決める
- 迷ったら1ファイルに詰め込まず、役割ごとに分割する
- 仕様変更がある場合は、`doc/specs/` と `doc/rules/` の両方を必要に応じて見直す

## まとまった作業や長くかかる作業の場合
- 最初にhandoverファイルを作成する
  - ファイル名は「YYYYMMDD_hhmm-件名」
- handoverファイルはサブタスクの着手時、完了時に更新する

## チーム運用

### 作業工程の順序

- 以下の順で作業を進める。ただし、必要に応じて反復する
  1. 計画
  2. マーケティングリサーチ
  3. 方針検討
  4. 要件定義
  5. 概要設計
  6. アーキテクチャ設計
  7. DB設計
  8. 詳細設計
  9. 実装
  10. テスト作成
  11. テスト
  12. テスト実施

### ブランチ運用ルール（GitHub Actions コスト抑制）

- **目的**: CI は main ブランチへの push / main 向け PR でのみ起動する。作業ブランチでの push では CI は走らない。これにより、push 頻度を制限せずとも CI コストを最小化できる。
- **main ブランチ直接作業の禁止**: 作業は必ず作業ブランチを作成して行う。main への直接 commit・push は禁止する。
- **ブランチの作成単位**: issue 単位で1つのブランチを作成する。1つの issue に対して複数ブランチは作らない。
- **ブランチの命名規則**: `issue/<issueフォルダ名>` とする（例: `issue/20260720_01_fix_issue11_defects`, `issue/20260722_01_web_feature_parity`）。
- **作業ブランチでの push**: 自由に行ってよい。こまめに push して作業中断耐性を確保する。CI は走らないためコストは発生しない。
- **main へのマージ**: そのissueの作業がレビューまで完了した場合にのみ main へマージする。
  1. issue内の全サブタスクが完了している
