# 外部データ連携のガバナンス要件

## 1. 目的と適用範囲

本書は、pakulistが後続フェーズでX APIまたはX Contentを利用する場合の、データ最小化、保持、削除、再配布、資格情報、アクセス制御、監査、インシデント対応の要件を定義する。現行OSS MVPはローカルファイルをブラウザ内で処理するだけであり、本書のサーバー側要件を実装しない。

> **法務上の注意**: 本書はX公式の開発者文書を根拠としたプロジェクト要件の草案であり、法的助言ではない。外部データ取得・保存・公開の開始前に、適用されるXとの契約、Developer Policy、Developer Agreement、個人情報保護法制を有資格の専門家と確認する。

## 2. 前提条件

外部データ連携は、`x_data_acquisition_policy.md` のDAR-01〜DAR-10を満たし、次のゲートをすべて通過した場合にだけ開始できる。

| ゲート | 条件 |
| --- | --- |
| 利用目的の承認 | Xへの利用目的の開示と、重複投稿候補の収集・分析・表示についてDeveloper Policy上必要な書面許可を取得している。 |
| データソースの承認 | 公式X APIだけを使用し、取得対象・検索条件・期間・エンドポイントが記録されている。 |
| 設計の承認 | 本書の保持・削除・資格情報・アクセス・監査の要件を実装設計とテストへ落とし込んでいる。 |
| 運用の承認 | 予算上限、レート制限、削除要求、インシデント時の連絡先と停止手順が定義されている。 |
| 販売・課金の承認 | 有効な料金カタログ、従量課金又は定額利用枠、見積り・予約・精算・停止、決済・税・調整の責任分界が承認されている。 |

## 3. データ分類と最小化

| 区分 | 例 | 取扱い |
| --- | --- | --- |
| X Content | Post ID、本文、投稿URL、投稿日時、アカウント識別子、公開メトリクス | 事案ごとの検出・証拠整理に必要な最小項目だけを取得する。DM、保護Post、不要なプロフィール項目、位置情報は取得対象外とする。 |
| 導出データ | 正規化テキスト、類似度、クラスタID、取得条件、判定設定 | X Contentから分離して保存し、本文を含めない形で可能な限り再現性を確保する。 |
| サービス利用者データ | 利用者ID、同意記録、事案名、操作記録 | X Contentと論理的に分離し、目的外利用を禁止する。 |
| 秘密情報 | APIキー、Bearer Token、OAuthトークン、暗号化鍵 | ブラウザ、リポジトリ、ログ、エクスポート、Issue、PRへ保存・出力しない。 |

GOV-01: 取得クエリには対象アカウント、期間、キーワード、目的コードを必須とし、空の条件・全量条件・継続監視条件を受け付けない。

GOV-02: Protected Account、DM、ブロックによって見えないContentを、別のトークンやデータ源と組み合わせて閲覧・保存・表示してはならない。

GOV-03: X API取得Postを、広告ターゲティング、人物属性の推測、基盤モデルの学習・ファインチューニング、Xの可用性・性能の測定に利用してはならない。

## 4. 保持・削除・再取得

### 4.1 保持期間

| データ | 初期上限 | 終了・短縮条件 |
| --- | --- | --- |
| API取得X Content | 30日 | 検出事案の終了、利用者の削除要求、X Contentの削除・保護化・利用不能化、またはX／対象アカウントからの削除要求のうち最も早い時点。 |
| 導出データ | 90日 | 対応するX Contentの削除後は、本文・アカウント・URLを含まない集計済みの品質指標だけを保持できる。事案の削除要求時は削除する。 |
| 操作・監査ログ | 90日 | セキュリティ調査・規約対応でより短い期間が求められる場合は短縮する。本文、URL、トークンを記録しない。 |
| 秘密情報 | 利用中だけ | 失効、ローテーション、権限剥奪、インシデント時に直ちに無効化・削除する。 |

GOV-04: X Contentが削除、保護化、停止、またはAPIから利用不能になった場合、サービスは次回同期時に閲覧対象から除外し、遅くともXまたは対象アカウントからの削除要求を受けてから24時間以内に削除または非表示にする。

GOV-05: 保持期間の満了時は、X Content、派生コピー、検索インデックス、キャッシュ、エクスポート用一時ファイルを削除する。バックアップは暗号化し、復元時にも削除対象を再適用する。

GOV-06: 利用者または対象アカウントからの適法な削除要求を受ける窓口、本人確認、受付時刻、対応期限、完了通知を運用手順に定義する。

### 4.2 再配布と出力

GOV-07: API取得X Contentを第三者へ提供する標準出力は、Post ID、URL、アカウント、取得時刻、検出根拠とする。本文などのPost Objectを含むダウンロード・API・レポートは、Xの再配布条件、利用者権限、件数、方法、書面許可を確認してから個別に有効化する。

GOV-08: 現行のローカルファイル由来のCSV出力と、将来のAPI取得データ由来の出力を同一の権限・保持・再配布条件として扱ってはならない。データソースと出力制約をメタデータで区別する。

GOV-09: X Contentを画面表示する場合は、Xを出所として明示し、表示の直前または定期的に最新状態を確認する。削除・保護化したContentは表示しない。

## 5. 資格情報とアクセス制御

GOV-10: APIキー、Bearer Token、OAuthトークンは、サーバー側のシークレットストアだけで管理する。クライアント、CSV/JSON、ブラウザストレージ、ソースコード、CIログ、監査ログへ露出してはならない。

GOV-11: 開発、ステージング、本番には用途を明示した別アプリ・別資格情報を用意し、本番資格情報を開発環境へ持ち込まない。Xのポリシー上許容されるアプリ数・用途に従う。

GOV-12: 秘密情報へのアクセスは最小権限とし、担当者、目的、付与時刻、失効時刻を記録する。組織を離れた者、役割変更した者、漏えいが疑われる資格情報は直ちに無効化する。

GOV-13: 資格情報は少なくとも90日ごと、またはXの要件・インシデント対応で必要となった時点でローテーション可否を確認する。Xがローテーションを提供しない形式では、代替の失効・再発行・アクセス制御手順を文書化する。

GOV-14: 外部データ連携を利用するサービスでは、利用者認証、権限分離、事案単位のアクセス制御を実装するまで、複数利用者へX Contentを提供してはならない。

## 6. 監査・コスト・レート制限

GOV-15: 各API呼び出しについて、時刻、内部利用者ID、目的コード、エンドポイント、検索条件のハッシュ、件数、応答状態、消費量、レート制限残量、削除処理の結果を記録する。本文、URL、アカウント、トークン、認証ヘッダーをログへ書き込まない。

GOV-16: API使用量と費用は日次で集計し、予算上限の80%で警告、100%で取得を停止する。課金体系・単価は変更され得るため、実装・運用開始前にDeveloper Consoleと契約条件から設定する。

GOV-17: 429を受けた場合は`x-rate-limit-reset`を参照し、バックオフして再試行する。レート制限を超えようとするバッチ、並列化、複数アプリによる回避を禁止する。

GOV-18: 月次で、取得対象、保持件数、削除遅延、権限付与、資格情報ローテーション、費用、エラー、規約変更をレビューする。重大な逸脱時は取得機能を停止し、原因と再開条件を記録する。

GOV-19: 有償版のX API取得は、従量課金又は定額利用枠だけで提供する。取得前に、利用者ごとの見積り、残利用枠又は承認済み最大請求額、料金カタログの有効性、サーバー側の予約を原子的に確認する。利用枠又は請求上限の80%で警告し、100%又は原価・契約上限への到達時は次の取得呼び出しを開始しない。無制限取得、利用者承認なしの超過課金、クライアント主導の残量・価格判定を禁止する。

GOV-20: 課金・利用枠台帳は、予約ID、利用者ID、事案ID、プラン版、料金カタログ版、販売単位、予約・確定・解放数量、金額、通貨、状態、時刻、停止理由、管理者承認IDだけを記録する。本文、URL、アカウント、検索語原文、トークン、認証情報、決済手段の完全な情報を保存・出力しない。実行前の取消・期限切れ・消費なしでは未消費予約を解放し、同一冪等キーによる二重予約・二重請求を防ぐ。

## 7. インシデント対応

| 事象 | 初動 | 復旧条件 |
| --- | --- | --- |
| 資格情報の漏えい疑い | 該当資格情報を無効化し、外部取得を停止する。アクセスログを保全する。 | 新資格情報、影響範囲、再発防止策を承認する。 |
| 削除要求の未処理 | 該当Contentを直ちに非表示にし、削除キューを優先処理する。 | 24時間以内の削除、バックアップ・キャッシュへの反映、対応記録を確認する。 |
| レート制限・費用超過・利用枠上限 | 次の取得呼び出しを停止し、キューと未消費予約を保留又は解放する。 | レート・予算・利用枠・料金カタログ・クエリ最小化を見直し、利用者の追加承認又は管理者承認を確認する。 |
| 規約・利用目的との不整合 | 取得・表示・出力を停止し、Xへの通知・許可の要否を確認する。 | 利用目的・設計・許可条件を更新し、責任者が再開を承認する。 |

## 8. 現行MVPへの適用

現行OSS MVPでは、外部X APIを呼び出さず、入力データをサーバーへ送信・保存せず、資格情報・課金・利用枠を扱わない。このため、GOV-01〜GOV-20は将来の有償外部データ連携を実装する前の必須要件であり、現行MVPに保存・認証・収集・決済機能を追加する根拠にはならない。
