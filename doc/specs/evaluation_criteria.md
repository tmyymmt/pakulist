# 審査基準への適合性

複数カテゴリを横断する評価観点のため、`doc/specs/` 直下に配置する。

## ステータスの定義

| 表記 | 意味 |
| --- | --- |
| 方針確定 | 判断は済んでおり、根拠となる仕様ファイルがある。残るのは数値埋めや実装のみ |
| 一部確定 | 方向性は決まっているが、成立の裏付け（数値・検証結果）が未取得 |
| 未着手 | 実装または検討そのものが始まっていない |

「方針確定」は審査を通過できる状態を意味しない。実装・デモ・数値が伴って初めて満たしたと判断する。

## 一覧

| # | 審査基準 | ステータス | 確定している内容 | 残タスク |
| --- | --- | --- | --- | --- |
| 1 | 課題の実在性 | 方針確定 | X の規約上、複数アカウントからの重複・実質同一投稿はスパムとして違反行為に該当することを一次情報で確認済み。「検出対象は複数アカウント保有ではなく重複投稿」という整理も完了。→ `doc/research/20260811_x_rules_on_duplicate_posts.md` | 「困っている人が実在し、対価を払う」ことの裏付け（想定利用者へのヒアリング等） |
| 2 | ビジネス成立性 | 一部確定 | OSS（無償）+ クローズド有料の二層モデル、および課金対象を LLM 利用機能に置く方針を決定。→ `doc/specs/pricing/monetization_policy.md` | 課金モデル・価格帯・原価（#6 の結果が前提） |
| 3 | 完成度・デモの説得力 | 未着手 | なし（実装ゼロ） | デモシナリオの主軸を UC-01〜03 から選定 → 実装 |
| 4 | AIである必然性 | 一部確定 | 無償=決定的な一致判定 / 有料=LLM による意味的類似判定、という機能境界を確定。言い換え・表記揺れ・部分改変は決定的手法では検出できないという論拠を採用。→ `doc/specs/system_requirements/system_requirements.md` SR-P03, SR-D04 | 「決定的手法では実際に取りこぼす」ことを示す検証（少数サンプルでの比較で足りる） |
| 5 | 技術的な作り込み | 一部確定 | SNS 依存部分を差し替え可能にする方針（SR-01 系）、関係性可視化を見据えたデータ保持（SR-D05）を要件化 | 方式設計・詳細設計・実装 |
| 6 | LLMコスト | 一部確定 | LLM 呼び出しは OrcaRouter 経由に固定（SR-P04） | モデル選定、単価、1判定あたりのトークン量、想定利用量からの原価算出 |
| 7 | セキュリティ | 一部確定 | 自動通報を行わない（SR-C03）、規約準拠の取得手段とレート制限遵守（SR-C01/C02）、取得データの保持範囲・期間を定める（SR-C05）を要件化 | 認証情報の保管方式、保持期間の具体値、データ最小化の実装 |
| 8 | 次世代性・独創性 | 一部確定 | 差別化軸をアカウント間の関係性可視化に置く方針。ただし現バージョンではスコープ外 | 可視化を有料機能に含めるかの判断、デモに載せるかの判断 |

## 次に埋める順序（推奨）

1. **#6 LLMコスト** — 数値が出れば #2 ビジネス成立性が連動して埋まる
2. **#4 AIである必然性の検証** — 少数サンプルで決定的手法との比較を取る。#3 のデモ素材にもなる
3. **#1 の需要裏付け** — 規約面の裏付けは済んでいるので、残りは利用者側の声のみ
4. #3/#5/#7 は実装の進捗に合わせて更新する
